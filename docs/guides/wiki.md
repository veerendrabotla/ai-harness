# Repo Wiki Guide

`.aiharness/wiki/` — living documentation that lives **in your repository** and
is **auto-maintained by AI Harness runs**. After every completed run the
platform refreshes the generated pages; the agent authors topic pages on
request. This guide is the full reference: layout, ownership, the
pre-approved write zone, seeding, and troubleshooting.

> Related: [Hooks & Events](hooks-and-events.md) (the `afterComplete` hook that
> drives maintenance), [Permissions & Approvals](permissions-and-approvals.md)
> (the pre-approved zone), [Context & Memory](context-and-memory.md) (what
> reaches the model — the wiki is *not* injected).

---

## 1. What it is

| Property | Value |
|---|---|
| Location | `.aiharness/wiki/` inside the project root (repo-local) |
| Opt-in | The directory must exist — nothing is created until you seed it |
| Trigger | Every run that reaches `COMPLETED` fires the `afterComplete` lifecycle hook |
| Maintainer | `WikiMaintainer` (`backend/packages/agent-runtime/src/wiki-maintainer.ts`) — the hook bus's first production subscriber |
| Surfaces | Files only (no API/CLI/UI surface in v0.1 — read them in your editor, host them, commit them) |
| Context injection | **None.** The wiki is output for humans; steering still comes from workspace instructions and constraints |

Why a repo-local directory: unlike the knowledge base or project memory, the
wiki travels with the code — it reviews in PRs, versions in git, and renders on
any git host.

## 2. Layout and file ownership

```text
.aiharness/wiki/
├── index.md        # GENERATED — home page: topic-page TOC + recent runs
├── changelog.md    # GENERATED — one entry per completed run (newest first)
└── pages/          # AUTHORED — one markdown file per topic, by the agent
    ├── architecture.md
    ├── data-model.md
    └── ...
```

**Ownership is strict — this is what prevents merge chaos:**

| File | Owner | Rule |
|---|---|---|
| `index.md` | Platform | Regenerated after each maintained run. Do not hand-edit; prose goes in `pages/`. |
| `changelog.md` | Platform | Merged automatically (newest-first, idempotent per run, capped at 50 entries). |
| `pages/*.md` | Agent (and humans) | Free-form markdown. The maintainer never rewrites these — it only links them from the index. |

The generated `index.md` states this rule in its own header, so anyone opening
the file learns where to put content.

### What a generated changelog entry looks like

```markdown
<!-- run:4f9c2a10-8f3e-4b7a-9d21-1c6e2b9a77de -->
## 2026-10-02 — Add retry logic to the provider router

- Run `4f9c2a10` · 4 step(s) · verification 3/3 passed
- Touched: `backend/packages/model-adapters/src/router.ts`, `src/retry.ts`
```

The HTML comment is the idempotency marker — a replayed or retried run never
duplicates its entry. Goals are flattened to a single line and truncated at
120 characters before rendering, so a hostile or multi-line goal cannot inject
extra headings.

### What the generated index looks like

```markdown
# My project wiki

Living documentation for this repository, generated and refreshed automatically by AI Harness runs.
Topic pages are authored by the agent under `.aiharness/wiki/pages/`; ...

## Topic pages
- architecture — .aiharness/wiki/pages/architecture.md
- data model — .aiharness/wiki/pages/data-model.md

## Recent runs
| Date | Goal |
| --- | --- |
| 2026-10-02 | Add retry logic to the provider router |

---
_Generated by AI Harness · last maintained 2026-10-02T14:03:11.000Z (run `4f9c2a10`)_
```

## 3. How auto-maintenance works

```text
run reaches COMPLETED
  └─ orchestrator.fireHooks("afterComplete", ctx)        orchestrator.ts:930
       └─ WikiMaintainer.maintainFromHook(ctx)           runtime.ts (registered at startup)
            ├─ getProject → root + environment (LOCAL_BRIDGE | CLOUD_SANDBOX)
            ├─ list .aiharness/wiki/          → empty/absent ⇒ STOP (opt-in)
            ├─ gather run facts (goal, steps, verification, affected files)
            ├─ read changelog.md → merge entry (idempotent, capped) → write
            ├─ list pages/*.md → TOC
            ├─ query last 5 completed tasks → recent-runs table
            └─ write index.md
```

Details worth knowing:

- **Hook errors never fail runs.** `maintainFromHook` swallows its own errors
  (logging a warning), and `fireHooks` has a second guard
  (`orchestrator.ts:106-111`) — wiki maintenance is best-effort by design.
  Each maintenance write is attempted twice (one automatic retry after 1.5s),
  because a sandbox or bridge tool call can exceed its 30s timeout on a loaded
  machine while the executor is still spinning up.
- **Both execution environments are supported.** Cloud projects are written
  through the Docker sandbox; local-bridge projects through the bridge on the
  user's machine — the same `filesystem.list/read/write` tools the agent uses,
  with the same path confinement.
- **Presence is the switch.** If `.aiharness/wiki/` does not exist, the
  maintainer does nothing. Deleting the directory disables maintenance; no
  setting, flag, or migration is involved.
- **Idempotency.** A run recorded once is never recorded twice (marker match),
  but `index.md` is always refreshed (the recent-runs table and page TOC can
  change even when the changelog does not).
- **Growth is bounded.** The changelog keeps the newest 50 entries; older ones
  are dropped on merge. Git history is the permanent record.

## 4. The pre-approved write zone

By default `filesystem.write` is `WRITE` risk → **ASK** (an approval prompt for
every write). Wiki maintenance would park every run on its first changelog
write — so the permission engine grants a narrow pre-approval
(`backend/packages/permission-engine/src/evaluate.ts`):

> Writes whose target is inside `.aiharness/wiki/` return `ALLOW` without a
> rule.

Guardrails that keep this safe (all covered by `evaluate.test.ts`):

| Guard | Effect |
|---|---|
| Evaluation order | The zone is checked **after** explicit `DENY`/`ASK` policy rules — workspace policy can still deny or gate wiki writes |
| `.env` escalation | `.aiharness/wiki/.env` (or any `.env*` inside the zone) escalates to `ASK` as everywhere else |
| Traversal rejection | `.aiharness/wiki/../../secrets.md` is **not** in the zone → falls back to normal `ASK` |
| Prefix strictness | `.aiharness/wikifoo/x.md` is not in the zone |
| Executor confinement | Both executors re-confine every path to the project root (`confinePath` on the bridge, `sanitizeRel` in the sandbox) — the permission layer is a convenience, the executor is the boundary |
| Non-wiki tools unaffected | `filesystem.rename`, `filesystem.delete`, `terminal.run` etc. never get the zone |

One honest caveat: a model could read a secret (reads are `ALLOW` by default
platform-wide) and write it into a wiki page without an approval gate. The
exfiltration path still crosses `git.commit` (which **is** `ASK`), and wiki
content lands in your repo where it reviews like any other change — but if you
want zero unattended wiki writes, add an explicit `ASK` or `DENY` rule for
`filesystem.write` in your workspace policy and the zone stops applying.

## 5. Seeding a wiki (first run)

Maintenance is opt-in via directory presence, so seed once per repo:

**Option A — ask the agent (either environment):**

```text
Goal: Initialize the repo wiki at .aiharness/wiki/
Create .aiharness/wiki/pages/architecture.md documenting this repository's
major components and how they fit together, based on what you find.
Keep .aiharness/wiki/index.md minimal — it is regenerated automatically.
```

The agent's `filesystem.write` into `.aiharness/wiki/` is pre-approved (§4), so
this runs without approval prompts.

**Option B — by hand:**

```bash
mkdir -p .aiharness/wiki/pages
printf '# My project wiki\n\n<!-- seeded -->\n' > .aiharness/wiki/index.md
git add .aiharness/wiki
```

From the next `COMPLETED` run onward, `changelog.md` and `index.md` maintain
themselves.

**Suggested first topic pages:** `architecture.md`, `data-model.md`,
`conventions.md`, `decisions.md` (ADR-style entries the agent appends to).

## 6. What feeds a changelog entry

Each entry is assembled from data the run already produced (no extra model
calls):

| Field | Source |
|---|---|
| Date + goal | `Task.goal`, `Task.completedAt` |
| Step count | `afterComplete` hook payload (`orchestrator.ts:930`) |
| Verification passed/total | Hook payload + `VerificationResult` count for the run |
| Touched files | `TaskPlan.affectedFiles` (up to 5 shown, `+N more`) |
| Recent-runs table | Last 5 `COMPLETED` tasks for the project |

Failed runs do not fire `afterComplete` and therefore do not appear — the wiki
records the completed history, while failures live in the task timeline and
audit log.

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Nothing appears after runs | `.aiharness/wiki/` doesn't exist | Seed it (§5) — presence is the opt-in switch |
| Changelog not updating | Run ended `FAILED`/`CANCELLED` (no `afterComplete`), or a previous entry already holds the run marker | Check the task state; markers are by design |
| Writes fail on cloud projects | Sandbox image too old for nested `mkdir -p` (fixed in current images) or workspace materialization failed | Rebuild worker images; check worker logs for `wiki maintenance failed` |
| Writes fail on local-bridge projects | Bridge offline when the run completes | Start the bridge; maintenance simply skips while it's down |
| `index.md` overwrote my edits | `index.md` is generated | Move prose into `pages/*.md` (§2) |
| Wiki grows too large | Changelog is capped (50), but `pages/` is yours | Prune pages like any repo file |
| Want wiki writes gated after all | Add an explicit `ASK`/`DENY` rule for `filesystem.write` | §4 guardrail table |

## 8. FAQ

**Does the wiki reach the model's context?**
No. Nothing reads `.aiharness/wiki/` back into prompts — it is documentation
output. Steering remains workspace instructions (rank 2), goal, and
constraints; see [Rules & Instructions](../RULES_AND_INSTRUCTIONS.md).

**Is there a CLI or API for it?**
Not in v0.1. The CLI is a pure API client with no file access
([CLI Guide](../../CLI_GUIDE.md)), and the wiki lives in the repo, not the
database. Read it with your editor or git host.

**Can I move it elsewhere?**
The paths are constants in `wiki-maintainer.ts` (and mirrored by the
permission zone). Renaming means changing both — treat
`.aiharness/wiki/` as the contract for now.

**How do I turn it off?**
`rm -rf .aiharness/wiki` — absence stops maintenance permanently.

**Does it work with a repo that has no AI Harness project?**
No — maintenance runs from the worker's `afterComplete` hook, so the repo must
be connected as an AI Harness project (cloud or local bridge).

**What about commits?**
The maintainer never commits. Wiki changes land as working-tree edits — commit
them yourself or let the agent's `git.commit` step include them (that tool is
`ASK`, not pre-approved).
