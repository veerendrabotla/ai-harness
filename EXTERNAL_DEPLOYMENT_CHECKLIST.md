# EXTERNAL DEPLOYMENT CHECKLIST

Everything below requires **your** accounts/credentials. All code, configs and scripts are already prepared — follow top to bottom. Estimated manual time: ~45–60 min.

---

## 1. Prerequisites (one-time)

| Item | Where | Notes |
|---|---|---|
| GCP project + billing | console.cloud.google.com | Owner or Editor + Billing Admin |
| GitHub repo with this code | github.com | main branch |
| Resend account | resend.com | for password-reset / invite emails |
| (optional) Sentry + PostHog accounts | sentry.io / posthog.com | observability |

Install once locally: `gcloud` CLI + `terraform` ≥1.11.4.

## 2. GCP bootstrap (≈15 min)

```bash
gcloud auth login
gcloud config set project <PROJECT_ID>

# Enable APIs
gcloud services enable run.googleapis.com sqladmin.googleapis.com redis.googleapis.com \
  artifactregistry.googleapis.com iamcredentials.googleapis.com cloudkms.googleapis.com

# Terraform state bucket
gsutil mb -l us-central1 gs://<PROJECT_ID>-tfstate
```

## 3. Workload-identity federation for GitHub (≈10 min)

```bash
gcloud iam workloads-identity-pools create github --location=global
gcloud iam workloads-identity-pools providers create-oidc github-oidc \
  --location=global --workload-identity-pool=github \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository" \
  --attribute-condition="assertion.repository=='<ORG/REPO>'"
```
Create SA `github-deployer`, grant: `roles/artifactregistry.writer`, `roles/run.admin`,
`roles/iam.serviceAccountUser`, `roles/cloudsql.admin`, `roles/redis.admin`.
Copy the provider + SA emails → GitHub secrets `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT`.

## 4. Repository secrets / variables (GitHub → Settings → Secrets)

Secrets:
- `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT`
- `TF_VAR_db_password`, `TF_VAR_jwt_access_secret` (48B base64), `TF_VAR_csrf_secret` (48B base64), `TF_VAR_encryption_key` (32B base64), `TF_VAR_bridge_internal_token`

Variables:
- `GCP_PROJECT_ID`, `GCP_REGION`

Generate secrets:
```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64'))"   # JWT / CSRF / BRIDGE token
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"   # ENCRYPTION_KEY
openssl rand -hex 16                                                          # db password
```

## 5. Deploy (one click)

GitHub → Actions → **deploy** → Run workflow (environment `production` = manual approval).
Pipeline: builds/pushes api+worker+gateway images → terraform apply (SQL, Redis, Cloud Run).

## 6. Vercel hosting — services mode (frontend + API + bridge gateway, ≈10 min)

The repo ships a root `vercel.json` in **Vercel Services** mode: one project, one domain, three services.

| Service | Root | Public paths (top-level rewrites) |
|---|---|---|
| `frontend` | `frontend/` | everything else (Next.js) |
| `api` | `backend/apps/api` | `/v1/*`, `/healthz`, `/docs`, `/socket.io`, `/multiplayer` |
| `bridge-gateway` | `backend/apps/bridge-gateway` | `/bridge` (local-bridge pairing WebSocket) |

`api` reaches the gateway through a **service binding** (`BRIDGE_GATEWAY_URL` — injected at runtime, never set it by hand). The worker is intentionally **not** deployed to Vercel: it is a long-running BullMQ loop, not a request handler. Run it on any Docker host (one-liners above, or [self-hosting](docs/guides/self-hosting.md)).

1. vercel.com → Add New → Project → import this repo. Settings → General → **Framework Preset = `Services`** — without it Vercel ignores the `services` key in `vercel.json` and builds a single app instead of three.
2. Settings → Environment Variables (project-wide, all environments):
   - `NEXT_PUBLIC_API_URL=` — **empty string**: the frontend then calls same-origin `/v1/*` (fetches, OAuth links, socket URLs all resolve against the page origin).
   - `FRONTEND_ORIGIN=https://<project>.vercel.app` — **required**: the API skips the CSRF double-submit only for origins in this allowlist (the web client does not send `X-CSRF-Token`), and it also feeds CORS + socket.io origin checks.
   - Build/runtime secrets: `DATABASE_URL` (host-reachable Postgres), `REDIS_URL` (host-reachable, e.g. Upstash), `JWT_ACCESS_SECRET`, `CSRF_SECRET`, `ENCRYPTION_KEY`, `BRIDGE_INTERNAL_TOKEN` — generated by the §4 one-liners. The api build runs `prisma migrate deploy`, so `DATABASE_URL` must exist before the first deploy. Do **not** add `BRIDGE_GATEWAY_URL` (binding-injected).
   - Optional: `NEXT_PUBLIC_POSTHOG_KEY` / `NEXT_PUBLIC_POSTHOG_HOST`, `SENTRY_DSN`, `API_BASE_URL=https://<domain>`.
3. Deploy → copy the production domain. Frontend and API share the site, so plain `SameSite=Lax` cookies work — `COOKIE_SAMESITE=none` is **not** needed here (it stays only for split-origin hosting: Vercel frontend + API on another domain).
4. OAuth apps (GitHub/Google): redirect URI `https://<domain>/v1/auth/<provider>/callback` (served by the api service through `/v1/*`).
5. Verify: `https://<domain>/healthz` → `{"data":{"status":"ok",...}}`, `/docs` → Swagger UI, login from the app, `/socket.io` traffic, bridge pairing via `wss://<domain>/bridge`.
6. Pushes to `main` redeploy all three services (Vercel Git integration).

Caveats: Services is a **beta** feature; the api uses Vercel's Fastify preset (the documented `app.listen` pattern) — the first `vercel build` is the real proof, and the server entrypoint may need a small `VERCEL`-guarded export tweak if the adapter expects one. WebSockets (`/socket.io`, `/multiplayer`, `/bridge`) ride Vercel's public-beta WS support behind the rewrites; the client keeps a long-polling fallback. Not on Vercel: the worker (BullMQ consumer) — schedule the first run manually after deploy (tasks queue until it starts).

## 7. Post-deploy verification (≈5 min)

```bash
API=https://<api-url>
curl -s $API/healthz                                   # {"status":"ok",...}
curl -s $API/docs | head -1                            # Swagger UI HTML
npx tsx scripts/smoke-vertical-slice.ts $API           # all PASS
```
Then in the app: signup → connect a provider (or pair a bridge) → create workspace/project → run one real task end-to-end.

## 8. Optional integrations

- **Emails:** add `RESEND_API_KEY` + verified `RESEND_FROM` to Cloud Run api service; resend verification email flow.
- **Sentry:** set `SENTRY_DSN` on api+worker services.
- **PostHog:** set `NEXT_PUBLIC_POSTHOG_KEY` (+ host) on Vercel.

## 9. Rollback

Cloud Run revision traffic split (console or `gcloud run services update-traffic`); images are immutable per SHA tag.
